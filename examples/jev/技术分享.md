# Jev：把大模型从“生成答案”换成“提供可执行决策”

应用接入大模型后，常见链路是：拼 Prompt，让模型生成文本或 JSON，再校验、解析、重试，最后让业务代码据此分支。TypeSafe AI 的 Jev 改了这份契约：调用方提交一份 **state（待判断的状态）** 和若干个 **类型化问题**，模型直接返回选项、分数或真假概率。它不负责写回复、代码或推理说明，而是给软件一个可检查、可组合的决策结果。TypeSafe 将这类产品称为 [System One 模型](https://docs.typesafe.ai/concepts/system-one.md)：像人的快速直觉判断，专注于范围明确的问题。

## Jev 的基本模型

一次请求包含 `state`、`model` 和 `questions`。state 可以是文本，也可以是由字符串、对象、数组组成的 JSON；当前 Jev 只处理文本内容，不支持图片、音频和视频。所有问题共享同一 state，但彼此隔离、并行求值。因此可以在一次客服工单调用中同时判断负责部门、用户情绪、是否要求退款和问题严重度；新增问题几乎不增加响应时间，不过仍会增加 token 成本，也不会因问题之间互相引用而产生“上下文腐化”。

Jev 提供三种 [AI 原语](https://docs.typesafe.ai/introduction.md)：

| 原语 | 适合的问题 | 主要返回值 |
| --- | --- | --- |
| [Choice](https://docs.typesafe.ai/primitives/choice.md) | 从固定集合中选一项，如工单属于哪个部门 | 选中项、每项概率、置信度 |
| [Score](https://docs.typesafe.ai/primitives/score.md) | 在有序且有描述的等级上定位，如故障严重度 | 可落在等级之间的分数、各级概率、置信度 |
| [Noul](https://docs.typesafe.ai/primitives/noul.md) | 判断一个命题是否为真，如“客户要求退款” | “是”的概率，0 表示否，1 表示是 |

例如对“Safari 中导出会崩溃，但 Chrome 可用”的故障报告，Score 可以把等级写成“仅外观问题”“功能受损但有替代方案”“完全阻塞且无替代方案”。若结果在后两级的概率分别为 0.57 和 0.43，则分数是概率加权后的 1.43，而不是模型随意生成的“7 分”。这也解释了为什么等级应描述可观察的情形，而不是只写“轻微、中等、严重”。

Jev 的核心不只是类型，而是显式的不确定性。Choice 和 Score 返回完整概率分布，以及由分布形状计算出的 `confidence`：概率集中时高，摊平时低；Noul 的单一数值已经完整表达“是/否”分布，因此没有单独的 confidence。要特别区分：某选项的概率描述它有多可能，confidence 则概括整个分布有多集中；二者都不保证单次判断正确。[TypeSafe 的训练思路](https://docs.typesafe.ai/introduction/machine-learning-primer.md)称为 RLCD（面向校准决策的强化学习），目标是让一批预测中标为 0.8 的事件约有 80% 发生。概率校准本来就是分类系统中的独立能力，[scikit-learn 的说明](https://scikit-learn.org/stable/modules/calibration.html)也强调，能输出概率不等于概率天然可信。

## 它和其他模型方案有什么区别

**普通对话 LLM** 的目标是生成让人阅读的文本。它擅长解释、写作、开放式问答，但业务程序必须从生成内容中恢复决策。Jev 的答案空间由调用方预先定义，输出可以直接进入 `if`、排序和路由逻辑；代价是它不会生成面向用户的回复，也不会说明理由。

**LLM + Structured Outputs** 已经能按 JSON Schema 保证字段、枚举和类型合法，避免格式错误与相应重试，这是非常实用的工程方案。[Structured Outputs 文档](https://developers.openai.com/api/docs/guides/structured-outputs/)解决的是“生成结果是否符合结构”；Jev 进一步把任务限制为 Choice、Score、Noul，并把每个候选结果的概率及不确定性作为一等输出。换句话说，前者可以稳定地产出一个合法的 `department: billing`，后者还意在告诉代码 `billing` 与其他部门各占多少概率，以及是否该自动执行。反过来，如果需要抽取任意字段、生成嵌套对象或文字内容，JSON Schema 方案更通用。

**推理模型** 会先使用内部推理 token，适合规划、工具调用、编程、科学问题和多步代理工作流；它以更多计算换取复杂问题求解能力，参见 [Reasoning models](https://developers.openai.com/api/docs/guides/reasoning/)。Jev 面向的是几秒内可做出的原子判断。遇到“综合市场规模、技术可行性和差异化评价创业项目”时，Jev 的推荐做法不是让模型长链推理，而是拆成三个独立 Score，再由代码设置权重。权重和规则可审计、可修改；但若任务本身需要搜索、证明、规划或处理前后依赖，推理模型更合适。

**传统分类器或评分模型** 同样能给标签和概率，并可额外做概率校准。它通常围绕固定特征、标签和训练流程构建；Jev 的产品接口则保留自然语言理解能力，让开发者用 instructions 和 criteria 定义判断边界，并在一次调用中混合多类问题。两者并非谁全面替代谁：当任务极稳定、数据充足且需要完全自有训练与部署时，专用分类器仍可能更合适；当规则难以穷举、输入是自然语言、又希望较快建立类型化决策接口时，Jev 更值得验证。

## 正确的工程用法

第一，把复合问题原子化。“客户愤怒且要求退款吗”应拆成两个 Noul；“候选人总体如何”应拆成经验、技能匹配等 Score，再由代码组合。这样每个答案含义明确，业务权重也不会藏在 Prompt 中。

第二，让选项互斥且边界具体。Choice 的描述要指出覆盖与不覆盖的情况，集合可能不完整时加入 `other` 或 `none of the above`。Score 每级应写现实情形，并坚持一个维度。问题设计仍需用自己的样本测试；高 confidence 只说明分布集中，不证明题目设计正确。

第三，把不确定性变成控制流。可将结果分为三档：高置信度自动执行，中等置信度要求确认或补充信息，低置信度转人工或其他模型。阈值应随风险变化：展示错页面容易恢复，阈值可以较低；退款、转账等高风险动作应采用更高阈值和确定性校验。[Confidence 指南](https://docs.typesafe.ai/confidence.md)明确建议从保守阈值开始，用本域数据调整，而不是复制一个“万能数字”。

## 什么时候值得尝试

如果你的系统面对自然语言输入，输出最终要驱动分类、打分、审核、排序或路由；答案空间能预先描述；吞吐和延迟重要；并且你愿意为“不确定”设计人工、澄清或推理模型兜底，那么 Jev 很匹配。客服分流、内容审核信号、线索评分、简历条件核对和工单优先级，都是典型形态。

如果目标是生成回复或代码、抽取开放结构、执行多步推理，或者必须处理多模态输入，就不应把 Jev 当作通用 LLM 的替代品。更现实的架构是分工：Jev 做快速、可观测的窄决策；确定性代码执行规则；推理模型处理疑难案例；人负责高风险和低置信度样本。判断是否采用它的关键，不是“它是否更聪明”，而是你的问题能否被写成清晰的类型、候选边界和风险阈值——如果可以，Jev 提供的是一种更贴近生产软件的 AI 接口。
