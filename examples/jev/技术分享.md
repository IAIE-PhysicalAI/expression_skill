# Jev：让大模型输出可执行决策

接入大模型 API 时，我们通常让模型生成文本或 JSON，再做校验、解析和重试，最后由业务代码决定下一步。TypeSafe AI 的 Jev 换了一种接口契约：调用方提交一份 `state`（待判断的状态）和若干类型化问题，模型返回选项、分数或真假概率。它不写回复、代码或推理说明，而是给程序可直接检查、组合的决策结果。TypeSafe 将它称为首个 [System One 模型](https://docs.typesafe.ai/concepts/system-one.md)，强调像直觉一样快速处理范围明确的判断。

## Jev 如何表示一个判断

一次请求包含 `state`、`model` 和 `questions`。`state` 可以是字符串，也可以是由文本组成的 JSON 对象或数组；Jev 当前不处理图片、音频和视频。同一请求中的问题共享 `state`，但相互隔离、并行求值。因此，一张客服工单可以同时判断负责部门、情绪、退款意图和严重度。根据[产品介绍](https://docs.typesafe.ai/introduction.md)，增加问题几乎不改变响应时间，但仍会增加 token 成本。

Jev 提供三种 AI 原语：

| 原语 | 适合的问题 | 返回结果 |
| --- | --- | --- |
| [Choice](https://docs.typesafe.ai/primitives/choice.md) | 从固定集合中选一项，例如工单归属部门 | 选中项、各项概率、`confidence` |
| [Score](https://docs.typesafe.ai/primitives/score.md) | 在有序且有描述的等级上定位，例如故障严重度 | 加权分数、各级概率、`confidence` |
| [Noul](https://docs.typesafe.ai/primitives/noul.md) | 判断一个命题是否成立，例如“客户要求退款” | “是”的概率，0 为否，1 为是 |

Score 最能体现这种设计。假设故障报告是“Safari 中导出会崩溃，但 Chrome 可用”，等级依次为“只影响外观”“功能受损但有替代方案”“完全阻塞且无替代方案”。如果后两级概率分别为 0.57 和 0.43，返回的 `score` 是等级编号的概率加权均值，即 1.43。它不是模型随意给出的“7 分”。因此，等级应描述可观察的情形，而不是只写“轻微、中等、严重”。

概率和 `confidence` 也要分开读。Choice 与 Score 返回完整概率分布；`confidence` 是对分布形状的摘要，概率越集中越高，越分散越低。Noul 只有“是/否”两个结果，一个数已经能完整表示分布，所以不另设 `confidence`。高 `confidence` 只表示模型的答案集中，并不保证判断正确。

TypeSafe 把 Jev 的训练思路称为 RLCD，即面向校准决策的强化学习：在一批预测中，被赋予 0.8 概率的事件应约有 80% 发生。这个定义针对一组预测，不能解释为某次结果“有 80% 保证正确”。概率校准也不是 Jev 独有的能力；[scikit-learn 的校准文档](https://scikit-learn.org/stable/modules/calibration.html)说明，一些传统分类器可以输出概率，也可以通过额外方法进行校准。

## 它与其他方案差在哪里

**普通对话 LLM** 面向开放式文本生成，适合解释、写作和问答。Jev 的答案空间由调用方预先定义，结果能直接进入 `if`、排序或路由逻辑，代价是不能生成面向用户的内容，也不会解释理由。两者解决的是不同环节：一个产出内容，一个提供受限判断。

**LLM + Structured Outputs** 可以保证响应符合 JSON Schema，避免缺少必填字段或出现非法枚举，减少格式校验和重试。这解决的是“输出是否符合结构”。Jev 则把任务进一步收窄为 Choice、Score、Noul，并把候选概率和不确定性作为标准返回值。例如，Structured Outputs 可以稳定生成合法的 `department: billing`；Jev 还会返回 `billing` 与其他候选的概率，供代码决定自动执行还是升级处理。反过来，需要抽取任意字段、生成嵌套对象或文字时，[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs/)更通用。现有材料没有两者的同题准确率对比，因此不能仅凭输出形式判断谁更准。

**推理模型** 会先使用内部推理 token，适合规划、工具调用、编程、科学问题和多步工作流。Jev 面向的是有充分上下文时，专业人员几秒内能完成的原子判断。比如评价创业项目，不让 Jev 一次权衡市场、技术和差异化，而是拆成三个 Score，再由代码设置权重。这样规则可检查、可修改；如果任务必须搜索、证明、规划或处理前后依赖，[推理模型](https://developers.openai.com/api/docs/guides/reasoning/)更合适。

**传统分类器或评分模型** 中，有些可以返回标签与概率，也可以通过额外步骤校准概率。Jev 的产品差异主要在接口：开发者用自然语言的 `instructions` 和 `criteria` 定义判断边界，并能在一次调用中混合多类问题。现有资料没有提供双方在数据需求、成本、准确率和部署上的统一基准，因此应按自己的样本和约束实测，不宜把 Jev 视为分类器的全面替代品。

## 工程上怎样用才合适

首先，把复合问题原子化。“客户愤怒且要求退款吗”应拆成两个 Noul；“候选人总体如何”应拆成经验、技能匹配等 Score，再由代码组合。权重与规则留在代码中，比藏在一个大 Prompt 里更容易检查和调整。

其次，明确答案边界。Choice 的描述应把相近选项区分开，集合可能不完整时增加 `other` 或 `none of the above`；Score 每级要写现实情形，并且一题只测一个维度。题目设计必须用自己的样本测试，高 `confidence` 不能证明等级或选项写得正确。

最后，把不确定性写进控制流。[Confidence 指南](https://docs.typesafe.ai/confidence.md)给出的起点是三档：高置信自动执行，中等置信要求确认或补充信息，低置信转人工或其他系统。阈值取决于风险：展示错页面容易恢复，退款、转账等动作则需要更保守的阈值和确定性校验。文档中的数字只是示例，实际值应从保守设置开始，用本域数据调整。

## 什么时候值得尝试

当输入主要是自然语言，输出用于分类、打分、审核、排序或路由，答案空间又能预先描述时，Jev 值得做一次小规模验证。它尤其适合一次要完成多个独立判断，而且系统已经为“不确定”准备了确认、人工或推理模型兜底的场景。

如果目标是生成回复或代码、抽取开放结构、完成多步推理，或者处理多模态输入，Jev 就不适合作为通用 LLM 的替代品。判断是否试用它，关键不在于“它是否更聪明”，而在于业务问题能否写成清晰的原子问题、候选边界和风险阈值。能做到这一点，Jev 提供的就是一种更贴近程序控制流的 AI 接口；实际效果仍要由本域样本验证。
