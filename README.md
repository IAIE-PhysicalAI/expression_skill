# 语言表达 · Chinese Expression

一套面向中文写作与润色的 Agent Skills，默认由当前一个 agent 完成写作、检查与修复；用户明确要求“严格校验模式”时，才启用一个提问／验收子 agent。现有示例聚焦技术分享文档：讲清一个技术或模型解决什么问题、如何工作、与其他方案有什么区别，以及如何判断它是否适合自己的场景。

围绕作者的核心想法选择信息、组织论证，在同一份文档上分阶段修改，让重点讲清楚、句间逻辑成立，并保留作者的语言风格。

**想法驱动，信息支撑。想法决定需要表达什么，逻辑决定如何组织与表达信息。**

技能主体、规则和使用提示均为中文。写作入口继续使用 `chinese-expression`，检查入口为 `chinese-expression-review`，两者配套安装。

当前测试分支为 **`gray/v3.1.1`**，两个 skill 的 `metadata.version` 均为 `3.1.1`。`main` 和正式 Release 仍为 **v2.0.0**，详见[更新记录](CHANGELOG.md)。

## 安装灰度版

### 获取并打包源包

从 `gray/v3.1.1` 测试分支获取新版。打包需要 Python 3.9 或以上，脚本只使用标准库；输出必须是源包之外的新目录，已有输出不会被覆盖。

```bash
git clone --branch gray/v3.1.1 --single-branch https://github.com/IAIE-PhysicalAI/expression_skill.git expression-skill-v3
git -C expression-skill-v3 rev-parse HEAD
python3 expression-skill-v3/scripts/package_skills.py --output ./expression-skill-v3-install
```

源包中的两个入口引用包根目录的共享规则，不能直接把单个源 skill 文件夹拷入技能目录。打包后得到两个配套目录，共享规则已分别放入各自的 `references/shared/`，检查方法的引用保留在两个同级目录之间。请配套安装。

### 使用 skills CLI 安装打包结果

需要能够运行 `npx` 的 Node.js 环境。在希望使用技能的项目目录中，将打包结果的路径传给安装工具：

```bash
npx skills add ./expression-skill-v3-install --skill chinese-expression chinese-expression-review --agent codex
```

如需跨项目使用，在命令末尾添加 `--global`。安装位置由安装工具和目标 agent 决定。

安装前可以只查看仓库中可用的技能：

```bash
npx skills add ./expression-skill-v3-install --list
```

### 手动安装与回退

将打包结果中的 `chinese-expression/` 和 `chinese-expression-review/` 两个完整目录放在目标 agent 技能目录的同一层级，保留各自的 `SKILL.md`、`references/`、`agents/` 和 `LICENSE`。两个入口的 `metadata.version` 应均为 `3.1.1`。

升级前备份定制内容，再整目录替换，避免遗留旧版混合验收文件。回退使用 [v2.0.0 正式包](https://github.com/IAIE-PhysicalAI/expression_skill/releases/tag/v2.0.0)，并移出 v3.1.1 专属的验收 skill，避免混用。备份保存在技能扫描目录之外。

当前灰度没有 v3.1.1 正式 Release，`releases/latest` 仍提供 v2.0.0。也可在测试分支页面下载源包 ZIP，再按上述方式打包；不要将默认主分支下载误认为本灰度版。默认流程使用当前 agent 的文件与任务所需工具，仅严格校验模式需要子 agent 调度能力。

## 使用

安装后，在支持技能调用的 agent 中指定 `chinese-expression`。Codex 中可以使用 `$chinese-expression`；其他工具按各自的技能调用方式使用。

当前 agent 按阶段读取方法，在同一份工作文档上完成准备、补充信息、内容编辑、检查和个性化风格。检查时重新读取保存后的正文，结论覆盖实际版本与范围，修复后回读并复验。

需要独立验收时，在请求中明确写出：

```text
请使用 $chinese-expression，以严格校验模式完成这项写作任务。
```

此时主 agent 创建并复用一个读取验收入口的提问子 agent。该模式仅在当前稿件任务中沿用；用户要求单 agent 或退出严格校验时，后续检查由当前 agent 接续。讨论或引用模式规则不构成启用请求。

### 润色已有文档

```text
请使用 $chinese-expression 润色 technical-share.md。
目标读者是有工程经验、第一次接触这个技术的同事。
重点讲清核心机制、适用条件，以及与现有方案的差别。
保留我的立场与语言风格，先保存大纲，再分阶段修改。
生成 technical-share-polished.md，并保留原文件。
可以补充公开资料；无法核实的信息请单独说明。
```

### 基于固定材料成稿

```text
请使用 $chinese-expression，根据 notes.md 写一份模型技术分享。
读者是应用开发工程师，重点解释输入输出、核心机制和选型依据。
只使用输入材料，不新增外部事实、数据或真实案例。
按流程保存大纲和正文；材料不足以支撑的判断请指出。
```

### 开放式写作

```text
请使用 $chinese-expression 写一份关于 TypeSafe AI 的 Jev 的技术分享。
面向使用过大模型 API 的工程师，回答它与其他模型方案有什么区别。
重点解释输入输出、决策方式、概率与置信度，以及它在软件中的作用。
从同一个任务出发，比较结构化输出的语言模型、推理模型和专用分类器。
先确认问题并保存大纲，明确重点、标题层级和需要补充的依据。
根据大纲搜集可靠依据，在同一份工作文档上完成起草、校验和风格调整。
语言直接、具体，关键概念要解释，厂商声明与独立测评结论要区分。
```

提供原稿、目标读者、核心想法、材料边界和风格参考，有助于 agent 判断重点与详略。

### 追问与局部改写

```text
请使用 $chinese-expression 修改现有稿件的第二节。
这一节已有结论，但实验介绍没有说明它为什么支持该结论。
沿用当前正文和大纲，只调整这一节及必要的前后承接，保留数据和限定。
```

只要求讨论或检查时，技能交付分析；明确要求修改时才接续编辑。局部改写使用原有大纲，在相关条目落实结构与重点变化，将当前有效的用户需求保存在文件末尾。

### 实验报告

```text
请使用 $chinese-expression，根据 experiment-notes.md 撰写实验报告。
面向第一次接触该实验的同事，说明目的、对象、方法、数据和结论。
只使用已有记录，保留样本范围、指标口径及结论限制，缺失信息请指出。
```

该请求会加载实验报告模块，默认由当前 agent 完成。模块不触发严格校验模式；如需独立验收，仍须明确要求该模式。

## 工作流程

七个步骤保持原有阶段边界，默认由当前 agent 顺序执行；严格校验模式才将检查交给提问子 agent：

| 阶段 | 默认执行者／严格模式执行者 | 需要完成的工作 |
| --- | --- | --- |
| 准备：第一至三步 | 当前 agent／主 agent | 理解核心问题和材料，保存重点、段落作用和展开关系；文件末尾单列用户需求 |
| 补充信息：第四步 | 当前 agent／主 agent | 按重点补充和核实材料，记录依据、出处、条件和缺口 |
| 内容编辑：第五步 | 当前 agent／主 agent | 选择、解释和组织信息，写回同一份正文及必要大纲调整 |
| 组织验收：第六步前半 | 当前 agent／提问子 agent | 从实际正文判断主线、层级、重点与段落作用，再对照必要大纲 |
| 支撑验收：第六步后半 | 当前 agent／同一个提问子 agent | 逐句检查信息、推理、依据、忠实性与必要限定 |
| 个性化风格：第七步 | 当前 agent／主 agent | 按作者声音调整表达，保存后按当前模式复验 |

大纲明确标题关系、重点想说明的判断或问题，以及段落或段落组的作用。背景和过渡交代服务对象，不必各自提出观点，也不预先固定所有自然段。用户需求单列在文件末尾，只维护当前有效要求；后续局部改写在原纲要中修改相关部分。

每轮修改针对具体问题。依据不足就补充材料，影响理解的信息孤立就补足解释与关联，句间推理不成立就重新组织。已符合要求的内容保留，不为增加轮次而强行修改。

进入相应阶段才读取对应文件。全程[表达原则](shared/表达原则.md)与[交接协议](shared/交接协议.md)共同维护；[修改后复验](skills/chinese-expression-review/references/修改后复验.md)检查原问题及关联影响。默认由当前 agent 回读确认后关闭问题；严格校验模式由提问方确认，写作方不能以完成声明代替复验。

任务目标用于理解文章方向，不转成固定观点、切入点、必写内容或评分表。验收仍采用技能已有的组织、解释、逻辑、支撑、事实与原意等判断条目，允许不同但成立的表达方案。

第六步也检查“不是……而是……”“并非……”等正反表达：保留理解所必需的区分与证据边界，将可直接表达的观点改为正面陈述，处理重复防备与虚设反方。此项随逐句验收执行，不设句式数量阈值。

## 中文表达规则

- 优先使用准确、已解释且常见易懂的词语；影响理解的辅助概念也须按需解释，同一概念统一称呼，相似概念分清含义。
- 删除重复与空泛内容，为重要但抽象的判断补足具体解释。
- 根据实际逻辑决定是否使用关联词，避免把相关、先后发生或用词相近写成因果与递进。
- 正面陈述优先，避免反复使用“不是……而是……”等防备性表达；必要的反面说明集中后置。
- 核实新增的事实、数据、引用与真实案例，保留原意、适用条件和确定性程度。
- 在全文、段落和句子三个层面检查信息是否支撑观点，避免关键概念、数据或判断孤立出现。

这些规则贯穿全程；最后的风格阶段处理作者个性化的表达特点。

## 环境与适用范围

技能使用通用的 [Agent Skills 格式](https://agentskills.io/)，核心指令位于 `SKILL.md`。`agents/openai.yaml` 提供 Codex 的展示信息；其他工具可能忽略该文件。

默认执行需要文件读写能力；开放式写作和外部核验还需要搜索、读取来源的能力。仅严格校验模式需要子 agent 调度能力。技能本身不附带模型、搜索服务或文档编辑软件。严格校验无法完成时可继续写作与自检，并说明独立验收未完成。

独立上下文仍取决于宿主的派发方式，只读职责也不等于文件权限沙盒。格式校验或完成流程不保证内容没有遗漏；涉及事实的稿件需依据原始来源检查。源包打包脚本只处理发布目录，不承担运行时写作、判断或调度。
