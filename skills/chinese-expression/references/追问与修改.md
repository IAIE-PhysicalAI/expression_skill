# 追问与修改

用于接续已有稿件上的讨论和修改。先理解用户这次希望改什么、达到什么效果、保留什么，再进入相应阶段；持续使用同一份工作稿。检查与复验通过主入口调度独立的验收 skill。

## 识别请求并读取当前内容

用户只询问文意、来源位置或已作修改的理由时，主 agent 读取回答所需内容后直接解释。仅讨论、比较写法时交付分析，不据此写回文档。要求核验依据、检查结构、逻辑、支撑或忠实性时，向唯一的提问 agent 派发指定检查，主 agent 转交结果；不自动修复、强制新建大纲或完成未请求的检查。用户提出修改要求，或结合上下文已经明确表达修改意图时，接续编辑；仅补充材料而未说明用途时，结合上下文判断其作用，不自动把全部材料加入正文。

每次接续编辑前，实际读取已保存的当前工作稿。结合对话定位“这一段”“刚才那句”等指代；位置明确时直接使用，实质歧义才询问。当前文件可能包含用户自行作出的修改，不能以记忆或聊天中展示的旧文本覆盖它。

- 局部修改读取目标所在完整段落、必要的前后承接及相关大纲；不能仅搜索一句话后直接替换。
- 涉及章节关系、主线、读者或全文风格时，按判断和修改需要扩大读取范围，必要时读取全文及完整大纲。读取范围不等于允许改写的范围。
- 初始原稿和原始材料用于核对原意、事实、材料边界或作者原有风格，涉及这些判断时按需重读。当前工作稿仍是编辑起点，不用初始原稿覆盖已经成立的修改。
- 后续阶段读取自己的最新输入，验收与复验按《交接协议》重新读取保存后的真实内容。

## 必要时与用户确认

结合用户请求、当前内容、原稿或参考文本及已有明确偏好，判断修改要求是否足够清楚。只有不同理解会实质改变语气方向、原意、读者定位、修改范围或重要约束时，才暂停相关修改并询问。

从实际存在且无法可靠推断的问题中，选择对本次修改影响最大的至多三项；只有一项就问一项。问题的顺序由具体任务决定，不预设通用优先级。多种合理写法本身不构成询问理由，已有答案不重复确认。

说明需要用户决定的事项及其对修改的影响，不先生成候选正文让用户挑选。收到回复后据此确定修改要求并推进，无需再请用户审批接续阶段。

## 选择接续阶段并落实修改

对照当前成果与用户要求，判断具体差距以及哪个阶段负责解决。以实际工作需要选择阶段，不按“润色”“补充”“自然一点”等词语机械映射。多个相互依赖的阶段受影响时，从最早需要调整的阶段开始；仍然有效的大纲、材料和正文直接复用。

| 需要完成的工作 | 接续阶段及用户要求的落实方式 |
| --- | --- |
| 修正作者想法、读者、用途、材料边界或对输入的理解 | 准备第一、二步：用用户补充或确认的信息修正理解，更新相关写作安排；其余仍成立的安排保留 |
| 调整主线、层级、归属或重点详略 | 准备第三步：修改相关大纲，写清该部分要说明什么、如何展开，再检查由此产生的材料需要 |
| 补充、提取、核实或替换依据 | 补充信息：把用户要求落实为具体信息缺口，在原有材料范围内查找，按已有授权开展外部检索，保存依据及其用途 |
| 已有信息足够，需要重新选择、解释或组织 | 内容编辑：对照用户期望定位当前表达的不足，调整相关段落的信息、解释、顺序或句间关系，写回当前正文 |
| 内容成立，只需调整语气、节奏、句式或作者声音 | 个性化风格：依据用户偏好及参考表达调整对应文字，保留事实、限定与原意；进入条件仍遵守风格阶段要求 |
| 用户要求检查结构、逻辑、支撑或忠实性 | 由提问 agent 执行指定内容验收，不预先假定正文有错；仅要求检查时由主 agent 转交结果，已授权修改时再由写作方回到对应阶段修复 |

写作方进入对应阶段后，读取本轮职责、当前成果及必要材料，将用户本轮要求作为具体目标：明确哪里需要改变、期望效果是什么、哪些内容必须保留。检查任务由提问方读取自己的职责与最新输入。要求不应被扩写为用户未提出的立场、固定答案或必写句子。

例如“这一段再自然一点”：若实际需要调整语气和节奏，由风格阶段处理；若生硬来自解释跳跃，由内容编辑补足已有信息之间的关系；若仍缺少依据，先进入补充信息。判断以当前文本及必要确认结果为依据。

追问引导的局部改写沿用原有大纲文件，不另建局部大纲或重建整份大纲。按《准备》的落盘规则更新文件末尾的“用户需求”；结构、重点与段落作用有变化时，仅修改原纲要中的相关部分。依据保存到原有材料记录，内容和风格写回同一工作稿。提问方读取重要的用户原话及有效要求，不靠写作方对追问的解释判断是否落实。各阶段处理必要的承接，保留仍有效的信息与表达。

## 让后续阶段使用修改成果

仅在实际需要按用户要求调整的阶段明确具体修改任务。写作方复用已有成果并保存变化；提问方在新的检查轮读取更新后的产物。按主入口复用本任务的提问 agent，不为每次追问另建检查者；不转交完整写作历史，也不强制建立独立状态文件。

交接按需说明提交版本、修改位置、需要复查的关联范围和未解决问题；提问方从大纲文件末尾及必要原始要求读取有效用户需求，包括成果中不易看出的保留要求与修改边界。需求或材料变化也可能使旧结论失效，即使正文尚未改动。

提问方继续使用原有通用标准，并检查本轮相关用户要求是否落实；两者都要满足。依据实际成果作判断，不能把编辑者的完成声明当作通过依据；检查、分歧、回退与复验统一按《交接协议》处理，无需另建验收失效表。

提问方发现旧问题或确认新的实际问题时，按《交接协议》交给写作方对应阶段处理；仅有疑似问题或个人写法偏好不足以新增修改目标。仅检查任务不进入修改。已授权修改时写回后重新验收，不能由写作方直接关闭问题。

由提问方完成必要验收且结论仍覆盖当前交付版本后，主 agent 直接交付，无需再询问是否满意或要求用户审批。仍依赖缺失材料或作者决定的问题按《交接协议》处理，不能记为通过。
